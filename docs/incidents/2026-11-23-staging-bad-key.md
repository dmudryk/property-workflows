## Підсумок

О 13:29 UTC новий деплой staging зібрався з хибним публічним ключем бази: перевизначення
`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` лише для гілки `staging` з одним зміненим символом. База staging відхиляла
кожен запит, тож вхід і всі сторінки з даними на staging не працювали **34,5 хв**. Червоний smoke і алерт у Telegram
прийшли **через 14 с** після того, як деплой став доступним. Розробник видалив перевизначення й зробив Redeploy — о
14:03:38 UTC smoke знову зелений. Попутно дріл показав дві вади сигналів: хибний алерт «production» (двічі) і
порожній журнал застосунку під час збою.

## Вплив (мовою користувача)

- **Хто:** усі, хто відкривав staging, — PM і розробник під тестовими акаунтами (`*@example.test`); реальних
  користувачів на staging немає. Приймання релізу PM у цей час не проводилось.
- **Що бачили:** сторінка входу відкривалась, але увійти, побачити шаблони, запуски й задачі чи розібрати документ
  було неможливо.
- **Скільки:** 34,5 хв (13:29:07 → 14:03:38 UTC; 15:29 → 16:04 за Києвом).
- **Дані:** нічого не втрачено й не змінено — збій відхиляв запити до бази, а не писав у неї. Міграцій не було.
- **Прод:** працював увесь час (`/api/health` → 200, `db: ok`). Але черговий двічі отримав хибне повідомлення
  «ЧЕРВОНИЙ SMOKE … production», хоча з продом усе було гаразд.

## Виявлення

- **Сигнал:** червоний smoke job `deploy` на адресу саме цього деплою (`client_payload.url`) → крок алерту в Telegram.
- **Час до виявлення:** від T0 (13:29:07) до алерту (13:29:21) = **14 с**. Ціль з #76 (≤ 5 хв) виконано.
- **Час до відновлення:** від алерту (13:29:21) до зеленого smoke (14:03:44) = **34 хв 23 с**; з них розбір агентом —
  14 хв, виправлення й збірка — ≈3 хв, решта — збирання доказів у межах години, поки живуть журнали Vercel.
- **Без сигналу:** сторінка входу відкривалась (`/` → 307, `/login` → 200), runtime-журнал деплою був порожній — до
  першої спроби PM увійти ніхто б не дізнався.

## Першопричина

| Твердження | Доказ |
|---|---|
| На деплої `kh13nidhn` база staging відхиляла публічний ключ | `/api/health` → 503, `reason: invalid-api-key` (прогін 45184389841, рядок 13:29:20); `classifyDbProbe` дає цю причину лише на відповідь «Invalid API key» від Supabase — `src/lib/health.ts` |
| Код між зеленим і червоним деплоєм не змінювався | обидва деплої зібрані з коміту `fa8b35d` (прогони 45173774800 і 45184389841, поле `sha`) |
| Адреса бази та сама — змінилось саме значення ключа | `supabaseRef: pqptodzkewlakfzumoos` в обох прогонах |
| Єдина зміна між збірками — перевизначення ключа лише для гілки `staging`, створене о ≈13:26 | список змінних у #76; інші змінні старші за 3 год; розбір агентом, розділ «Найімовірніша причина» |
| Значення `NEXT_PUBLIC_*` вбудовуються під час збірки, тож Redeploy підхопив хибний ключ, а старий деплой — ні | Vercel docs (release-guide WS11, «Змінні для гілки»); деплой 7f2m3id9t без перевизначення був зелений |

**Тригер:** нове перевизначення змінної для гілки `staging` + Redeploy.

**Що пропустило помилку в систему:** зміну змінної у Vercel ніщо не перевіряє до того, як деплой стає Ready і
забирає домен гілки: збірка успішна з будь-яким значенням ключа, а перевірка ключа є лише в smoke — уже після
перемикання домену.

## Усунення

- **Зупинили шкоду:** видалили лише перевизначення `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` для гілки `staging`
  (`APP_ENV` та інші змінні лишились) → Redeploy → staging знову бере загальне значення Preview, тобто ключ staging.
  Instant Rollback для staging недоступний (лише прод), а Redeploy старого деплою не допоміг би: збірка взяла б
  поточні змінні з хибним ключем.
- **Виправили вади сигналів:** PR #77 (див. «Дії»).

## Що спрацювало, що ні, де пощастило

- **Спрацювало:**
  - smoke кожного деплою: подія Vercel `repository_dispatch` → перевірка адреси саме цього деплою → алерт за 14 с;
  - `/api/health` з полями `appEnv` і `supabaseRef` одразу відрізнив staging від проду й показав, що база та сама;
  - профіль «лише пропонує»: агент назвав причину з доказами, знайшов хибний алерт проду, відмовився показувати
    змінну й робити відкат; зміну зробила людина;
  - діагностика кроку алерту (PR #74): до дрілу саме вона показала, що Telegram відхиляв повідомлення.
- **Не спрацювало:**
  - **хибний алерт «production»** (двічі): подія `status` від деплою staging запускала job `prod`, бо `branches`
    перелічує всі гілки, що *містять* коміт, — і `main` теж; job чекав на проді SHA staging;
  - **runtime-журнал зламаного деплою порожній**: `/api/health` повертав 503 без винятку й без запису, тож у Vercel
    Logs не було видно нічого; причину було видно лише в тілі health;
  - **health не називав змінну** — `invalid-api-key` треба було перекласти в «звірте `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`»;
  - **MCP Vercel** повернув 403 для команди `bravo16`: вхід OAuth не дав доступу до команди. Розбір пройшов на
    даних з GitHub і Vercel CLI, які вставила людина;
  - домен гілки `staging` перейшов на зламаний деплой: збірка не перевіряє ключ.
- **Пощастило:** це staging, а не прод; PM у цей час не проводив приймання; збій лише відхиляв запити й нічого не
  записав.
